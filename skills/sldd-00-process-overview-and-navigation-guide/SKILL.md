# Skill: SLDD Process Overview and Navigation Guide

---

## Language

Before any other action:

1. Detect the user's current language from their latest message.
2. Use that language for all replies, prompts, and generated files, and switch immediately if the user changes language.
3. If the language is unclear, ask once before continuing.

### Language Compliance Check

Before every user-facing reply:
- Ensure the entire reply is in the user's current language.
- Translate example wording rather than copying it literally from another language.
- Preserve structural tokens such as `##`, `- [ ]`, `- [x]`, `Step XX`, and path placeholders.

---

## Gate Enforcement

Apply these rules without exception:

1. Stop immediately if the user tries to skip required steps or approvals.
2. Do not allow Step 04 or Step 05 before Steps 01, 02, and 03 are completed and explicitly approved.
3. Do not mark any step `- [x]` without explicit user approval.
4. If existing implementation or a later completed step implies missing earlier approvals, warn about the violation and route back to the missing step.

---

## Start Or Resume Flow

Use this skill when the user is starting SLDD, resuming SLDD, asking which step comes next, or trying to jump ahead.

### Routing Order

1. Check for jump-ahead requests such as `implement`, `refactor`, `write code`, `write tests`, or similar, and enforce the missing earlier step.
2. Inspect the working tree and search the workspace recursively for `SPEC.md` files.
3. If implementation files are already changing and Step 01 is not approved, warn about a likely gate violation.
4. If any `SPEC.md` marks later steps complete while Step 01 is still incomplete, stop and report the violation.
5. If file writes are unavailable, explain that plan/read-only mode cannot save files and ask whether the user wants to start Step 01 manually.
6. If the user provides a specs root instead of a full `SPEC.md` path, list the available `SPEC.md` files under that directory and ask which feature to resume.
7. If exactly one `SPEC.md` already exists, read the checklist, verify Step 01 before trusting later completed steps, list completed steps, identify the next step, and resume there.
8. If multiple `SPEC.md` files are found and the correct feature is unclear, show the available features and ask the user which one to resume before proceeding.
9. Otherwise, use `docs/specs/<feature-slug>/SPEC.md` by default, unless the user explicitly provided another specs directory for the current flow. Create the file with the Progress checklist below, proceed to Step 01, and invoke the corresponding SLDD step skill.

```markdown
# SPEC: <feature name>

## Progress

- [ ] Step 01 — Product Intent Specification -> <link to file generated by step 01 if exists>
- [ ] Step 02 — High-Level Technical Design -> <link to file generated by step 02 if exists>
- [ ] Step 03 — Low-Level Design and Version Policy -> <link to file generated by step 03 if exists>
- [ ] Step 04 — Tests (written and confirmed failing)
- [ ] Step 05 — Implementation (all tests passing)
- [ ] Step 06 — Verification Report (gap report and go/no-go decision) -> <link to file generated by step 06 if exists>

```

## SLDD Steps

**Run one skill at a time. After identifying the current step, invoke that step's skill, review its output, and require approval before moving on.**

| Step | Skill | What It Does | Gate Requirement |
|------|-------|--------------|------------------|
| 01 | sldd-01-product-intent-specification | Problem, users, metrics, risks, acceptance criteria | User must approve before 02 |
| 02 | sldd-02-high-level-technical-design | Architecture, components, data flow | User must approve before 03 |
| 03 | sldd-03-low-level-design-and-version-policy | API contracts, data models, version policy | User must approve before 04 |
| 04 | sldd-04-tests-first-driven-by-acceptance-criteria | Write failing tests | No implementation code |
| 05 | sldd-05-minimal-implementation-to-pass-existing-tests | Minimal code to pass tests | Only after 04 tests exist |
| 06 | sldd-06-verification-and-feedback-report | Gap report, go/no-go | Final review |

---

## Approval Protocol

After any SLDD step produces output:

1. **Present the output** to the user
2. Say in the user's language that Step XX is ready for review and ask for approval or feedback.
3. Wait for explicit approval, then mark the step `- [x]`, save the file, and ask whether to proceed.
4. Use **sldd-98-approval-helper** for standardized approval, rejection, hold, and continue responses.

Never auto-proceed after approval or bypass the proceed prompt.

## Appendix

For existing codebases, use **sldd-99-existing-codebase-understanding-and-context-summary** after step 01 and before step 02 to ground all design decisions in the current architecture and conventions. Skip for greenfield projects.
